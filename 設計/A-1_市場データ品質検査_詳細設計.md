## 1. 目的・成功の意味

**長期目的**：BTC暗号資産FX市場の観測から仮説検証へ続く研究循環のため、時刻・価格・品質の意味を失わないデータ基盤を作る。

**今回の直接目的は2つ**：

1. 入力済みの**人工的なBTC想定1分足**が、明示した構造と時系列・数値の整合条件に適合するか確認する。異常を黙って補正せず、元データと検査結果を区別して残す。
2. GPTによる仕様・期待結果の事前確定 → Codexの小規模実装・実テスト → GPTによる証拠照合 → D1〜D7による修正 → C1〜C5による限定完成判定という**共同開発手順の実証**に利用する。

**成功しても意味しないこと**：実データの真実性、BTC FX商品の選定、取引所との実接続、市場状態の正しい解釈、先読みが存在しないことの全体保証、収益性、デモ／本番取引の安全性。

## 2. 責任境界と接続関係

```text
［人工CSV／そのまま保管する元データ］
                  ↓
［A-1：読み込み・仕様検査・品質レポート］
      ├─ INVALID → 問題の種類・対象行を保存／後工程へ利用許可を出さない
      └─ VALID   → 元CSVの参照とハッシュ・時刻／商品情報・品質レポート
                        ↓
          ［Bのための模擬受け手：受信契約だけを試験］
               ※実際の市場状態計算Bは未実装
```

- **A-1の責任**：入力の構造、時刻、欠損・重複・順序、OHLCVの基本的整合を検査して品質判定を行い、根拠を残す。
- **A全体の未実装部分**：実API取得、外部データ保存パイプライン、データ更新、各取引所・商品の意味付け、長期時系列の管理など。
- **B以降の責任ではない**：方向分類、予測、LONG/SHORT/NO TRADE、売買、研究仮説、利益計算。E/Gとの本接続も対象外。
- **安全上の禁止**：INVALIDデータを自動で有効化しない。欠損補間や時刻並べ替えによって元入力を改変しない。取引API、認証情報、ネットワーク経由の取得、実発注機能を追加しない。

| 識別 | dataset_id=`synthetic-btc-1m-001`、instrument_id=`BTC_SYNTHETIC`、source_kind=`SYNTHETIC` | 人工データと実市場データの混同を防ぐ。CSVとは別に入力条件として与える |

## 4. 入力契約

入力CSVの列は**この順序・この名前**とする（今回の採用範囲）。UTF-8（BOMなし）、ヘッダーあり。**データ領域の空の物理行は構造不正**とし、通常の行末改行は空行と扱わない。対象バイトを読めたがUTF-8に復号できない場合やBOM付きの場合は `SCHEMA_ERROR` で品質INVALIDとする。ファイルの欠如・アクセス拒否など**ファイルを取得できない処理障害**とは区別する。各時刻は末尾が文字 `Z` の秒精度UTC表記に固定し、空白やタイムゾーンなし表記、`+00:00`表記も初回契約では受け付けない。これは**文字列形式**の検査であり、時刻ラベルが実際のUTCを示しているかまでは証明できない。

```csv
bar_start_utc,available_at_utc,open,high,low,close,volume
2026-10-01T12:00:00Z,2026-10-01T12:01:02Z,100,105,99,103,1.0
2026-10-01T12:01:00Z,2026-10-01T12:02:02Z,103,106,101,102,0
2026-10-01T12:02:00Z,2026-10-01T12:03:02Z,102,104,100,101,2.5
```

**上記の値は市場価格ではない。** 価格の刻み幅、出来高の測定単位、商品の契約仕様を意味しない。

入力時にはCSVのほか、**期待時間範囲** `[expected_start_utc, expected_end_utc)` を外部条件として必須指定する。上例では `[2026-10-01T12:00:00Z, 2026-10-01T12:03:00Z)`。`dataset_id`・`instrument_id`・`source_kind`・`timeframe_seconds` も入力設定として明示し、今回は `BTC_SYNTHETIC`／`SYNTHETIC`／`60` に固定する。これらの設定値と検査規則版はレポートへ写すが、**CSVのSHA-256だけでは設定の正当性を証明できない**。

時刻の意味：
- `bar_start_utc`：集計区間の開始。例えば12:00は **[12:00, 12:01)** の足を指す。
- `bar_end_utc`：CSVには保存せず、`bar_start_utc + 60秒` で導出する。
- `available_at_utc`：その確定足が**利用可能になったと想定する時刻**。人工データでは合成した値であり、実市場で利用できた時刻の証明ではない。
- **B側の判断時刻**はA-1の入力ではない。Bの模擬受け手は `bar_end_utc <= decision_time` かつ `available_at_utc <= decision_time` だけ使用できることを試す。`available_at_utc` は**Bの足選別で使用する値**で、人工データの外部真実性を裏付けるものではない。未来の利用可能時刻があるだけではA-1の品質不合格にしない。

**時点別品質と全量品質の区別**：A-1の `quality_passed` は指定窓の**全行を検査した事後の全量判定**であり、判定時刻Tで実際に利用できた情報だけから得られた状態を表すものではない。模擬Bの行選別テストを「先読みを起こさない歴史的判断の実証」と解釈しない。将来、Bで履歴時点Tの判断・検証を実施する場合、Tより後にしか判明しない行・全量検査の結果・集計情報を使用しないための、時点別入力集合・品質判定とその再現方法を別途設計・実証する。

## 5. 必須の検査ルール

| ID | 検査対象 | 合格条件 | 失敗時の例 |
|---|---|---|---|
| V1 | CSV構造 | 必須7列が完全一致、全行で欠損や余分なセルなし、少なくとも1件 | `SCHEMA_ERROR`、`EMPTY_DATASET` |
| V2 | 時刻書式 | `bar_start_utc` と `available_at_utc`、設定の期待窓が厳密な秒精度UTC `...Z` で妥当。足開始と期待窓の両端は分境界 | `INVALID_TIMESTAMP`（データの時刻）、設定不正は処理障害 |
| V3 | 時系列 | 入力行は開始時刻の**厳密な昇順**、開始時刻の重複なし。開始時刻が一致する行は `DUPLICATE_BAR`、前行より小さければ `OUT_OF_ORDER`。非隣接の重複も検出する | `OUT_OF_ORDER`、`DUPLICATE_BAR` |
| V4 | 区間の完全性 | 指定した `[start,end)` の**各1分開始時刻にちょうど1行**、範囲外なし | `MISSING_BAR`、`OUT_OF_RANGE` |
| V5 | 価格 | O/H/L/Cが有限の十進数かつすべて `> 0`、`low <= min(open,close) <= max(open,close) <= high` | `INVALID_PRICE`、`INVALID_OHLC` |
| V6 | 出来高 | 有限の十進数で `>= 0`、**0は正常値** | `INVALID_VOLUME` |
| V7 | 利用可能時刻 | `available_at_utc >= bar_start_utc+60秒`。実際の配信時刻を保証するものではない | `PREMATURE_AVAILABILITY` |
| V8 | 不変性 | CSVを自動ソート／補完／上書きしない。**CSVを一度読み取った同じバイト列**からSHA-256を計算し、そのバイト列を復号・検査する。ハッシュ計算後にファイルを再読込して別の内容を検査しない。入力ファイルを変更してしまった場合は品質上の不合格ではなく**実装・処理障害** | `INPUT_MUTATED`（実装異常としての試験上の判定） |

補足：入力時間範囲は `start < end` とし、両端をUTCの分境界にそろえる。指定範囲内で欠損した最初・最後の足も検出する。検査失敗時も、可能な範囲で行番号とエラーコードを返し、秘密情報や巨大なデータ全文をレポートへ複製しない。未知の入力形式や処理途中の失敗を、品質合格として扱わない。

**検査の独立性とエラー優先順位**：データの時刻が壊れていてV3・V4を安全に計算できない場合は、それらの従属検査だけスキップし、V2の異常を記録して全体をINVALIDとする。エラーは**CSV行番号昇順（行番号のない欠損等は最後）→エラーコード辞書順→対象の足開始時刻昇順**で並べ、同値が重なっても同一入力・設定で順序を再現可能にする。テストでは「必ず含むコード」と「必要に応じ併発する別コード」を区別する。CSV構造の破損がある場合の後続検査も同様。

## 6. 出力契約と障害時

今回の採用範囲ではJSONレポート1種類。出力先は入力とは別のパスとして指定。結果に最低限以下を含める。

```json
{
  "schema_version": "a1-quality-report-v0.1",
  "dataset_id": "synthetic-btc-1m-001",
  "instrument_id": "BTC_SYNTHETIC",
  "source_kind": "SYNTHETIC",
  "timeframe_seconds": 60,
  "validation_rules_version": "a1-v0.3",
  "expected_start_utc": "2026-10-01T12:00:00Z",
  "expected_end_utc": "2026-10-01T12:03:00Z",
  "rows_seen": 3,
  "raw_csv_reference": "<検査時に指定されたCSVへの参照。相対パス等。元データ本文は複製しない>",
  "raw_sha256": "<実際に読み込んだCSVのSHA-256>",
  "quality_passed": true,
  "issues": []
}
```

- `rows_seen` は**ヘッダーを除いた、CSVとして読取可能だったデータ行数**を指す。構造破損等で数を確定できない場合は `null` にでき、品質不合格とする。
- `issues` はJSON配列。各要素の必須フィールドは `code`（定義済みのエラーコード文字列）、`row_number`（CSVの**物理行番号、ヘッダーが1、先頭データが2**。該当行なしは `null`）、`bar_start_utc`（関連足の開始時刻文字列。特定不能は `null`）、`message`（人間向けの簡潔な説明文字列）とする。`MISSING_BAR` では `row_number=null` と欠損した `bar_start_utc` を必須とする。テストはまず `code`・対象行/時刻・判定を確認し、説明文の細かな言い回しに依存しない。正常時は `issues=[]`。
- `quality_passed=true` は**V1〜V8で定義したA-1の品質ゲートのみ合格**を意味する。Bでの利用時点の先読み防止や収益性を保証しない。**JSONの必須項目の欠落や型違反も模擬Bでは拒否**する。`schema_version` と `validation_rules_version` を区別し、双方を期待値と照合する。`quality_passed` は文字列ではなく真偽値、`rows_seen` は非負整数または `null`、`timeframe_seconds` は整数、`issues` は配列、`raw_sha256` は64桁の16進表現を使う。JSONの整数フィールドに真偽値を混入させない。**品質合格 `quality_passed=true` のとき `issues=[]` を必須とし、品質不合格 `false` のときは少なくとも1件の問題を示す。両者が矛盾する報告は模擬Bで拒否する。**`raw_csv_reference` は受信者が元CSVを見つけるための位置情報であり、**参照の存在・ファイルの同一性はB側でハッシュ照合する**。識別・期待窓・検査規則版などの設定値も受け渡し条件の一部である。
- 必須検査のいずれかに異常があれば `quality_passed=false` とし、`issues` にエラーコード、可能な行番号、簡潔な理由を入れる。**1件でも異常があれば今回のデータセット全体を不合格**とする（行単位の部分承認は将来課題）。
- CSV読込不能、設定値不正、JSON書込失敗などの**処理障害**は品質INVALIDと混同しない。レポート出力不能なら実行失敗として報告し、正常判定を残さない。CLIの場合は例として**終了コード0＝品質VALIDかつ書込成功、1＝品質INVALIDかつ不合格レポート書込成功、2＝処理障害**を固定し、実テストで確認する。品質INVALIDはテスト失敗を意味せず、期待どおりの検出ならテストPASSとなり得る。
- 同一入力・同一設定・同一実装版では**品質判定／issueコード・順序／入力ハッシュが再現可能**。診断の実行時刻など変動する情報は判定本文と混ぜない。CSVヘッダーのみなら `EMPTY_DATASET`、ヘッダーのない空ファイルなら `SCHEMA_ERROR` を一次コードとし、組み合わせを曖昧にしない。
- **新旧レポートの混同防止**：毎実行で新しい出力先を指定し、既存レポートへの無断上書きを拒否する。**完成したJSONだけを最終出力先に公開**し、途中失敗では当該実行の最終出力先に品質PASSレポートを残さない（仮ファイルがあれば別名で隔離）。Bの模擬受け手には、**同じ呼び出し処理が直前のA-1実行から得た終了コードと実際に作成されたレポートパス**を明示的に渡す。**終了コード0かつ、その実行が成功して生成した指定パス**でなければ、内容がVALIDに見えても受け取らない。呼び出し側は過去のレポートを黙って代用しない。単に新規名のファイルが存在するだけでは「今の実行結果」の証拠にしない。これはローカル模擬接続の処理契約であり、第三者による偽造への耐性を保証しない。
- 出力にAPIキー、実口座ID、生の市場大量データを含めない。入力とレポートの保存場所・ローカル権限を明確にする。元データの実運用用ファイルや機密データをGitへ公開しない。一方、**研究結果ではない少量の人工fixture**は自動テスト再現のためGit管理してよい。

## 7. 次のB機能に向けた**模擬接続**

Bそのものは実装しない。テストで**模擬受け手**を作り、次の契約だけ確かめる。

1. 呼び出し側が渡す**直前のA-1実行の終了コードが0**であり、その実行で完成・公開されたレポートパスに一致することを確認する。`quality_passed=false`、結果未存在、古いパスへの代用、JSONの必須フィールド欠落・型違反、`quality_passed` と `issues` の矛盾があれば受け取らない。
2. レポートの `raw_sha256` と受信する元CSVの実ハッシュが一致しなければ受け取らない。`raw_csv_reference` が存在しない、示すCSVが見つからない、またはレポートのJSONが壊れている場合も拒否する。SHA-256照合は**同一バイト列の確認**であり、データの真正性やレポートへの攻撃耐性を証明しない。模擬受け手は、呼び出し側から渡された**許可済み作業ディレクトリ**を基準としてCSV参照先を解決し、そこから外れたパスや `..` による逸脱を拒否する。パスはレポートの場所やプロセスのカレントディレクトリを暗黙の基準にしない。シンボリックリンク等を含め、正規化後の参照先が許可範囲内であることを確認する。
3. 対象データの `schema_version`、`dataset_id`、`instrument_id`、`source_kind`、`timeframe_seconds`、期待窓、`validation_rules_version`、時刻の意味を契約どおり解釈できる。人工実証では、期待と異なる識別情報や規則版のレポートを拒否する。
4. 判断時点 T より前に**区間が完了**し、かつ `available_at_utc <= T` の足だけ利用する。
5. 例：T=`2026-10-01T12:01:30Z` なら、上の正常CSVで利用可能なのは **12:00開始の足だけ**。12:01開始の足はまだ利用しない。境界値 `T=12:01:01Z` では未使用、`T=12:01:02Z` では12:00足が使用可能となることも確認する。

**過去時点の利用に関する限界**：模擬Bは行ごとの利用可能時刻を選別する試験用の受け手であり、A-1から渡される**全量判定がTより未来の情報を含み得る**。そのため、模擬Bを歴史時点Tにおける市場判断器として用いず、Tの時点で実際に選べたデータとその品質の証明には使用しない。例えば12:02足の異常は、12:01:30時点の12:00足を変えなくても全量 `quality_passed=false` に変えてしまう。この事実を明示して、未来の情報に依存した判断・検証をA-1の完成範囲から除外する。

この検証がPASSしても主張できるのは「人工データによる**模擬接続検証済み**」まで。「Bとの実接続検証済み」でも「実市場データの先読みなしを完全証明」でもない。

## 8. 事前固定する受け入れテスト（机上の期待値、未実行）

**正常入力に対する独立した期待値**：12:00から12:03の終端排他的3分間には開始時刻12:00、12:01、12:02の3本が必要（`(end-start)/60秒=3`）。例示CSVはこの3本があり、O/H/L/Cの上下関係を満たし、0出来高も合格。12:00足の区間終端は12:01:00、利用可能時刻は12:01:02で矛盾しない。

| テストID | 入力／条件 | 期待する結果 |
|---|---|---|
| T01 | 提示した3本の正常CSVと指定窓 | `quality_passed=true`、`rows_seen=3`、`issues=[]`、元CSV不変 |
| T02 | 12:01開始行を削除 | `MISSING_BAR`、品質不合格 |
