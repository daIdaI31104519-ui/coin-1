## 3. 入力契約と互換性

- CLI入力：`--record <既存JSONファイルへのパス>` を1件指定する。複数実験の一括集計はしない。
- **対応範囲を明示して固定**：`record_version == "0.1"`、`research.name == "breakout_connection_test"`、`research.version == "0.1"`、`research.simulation_only is True`、および次の `data` 属性に**すべて一致**する実装①の記録のみ：`source == "synthetic_fixture"`、`market == "synthetic_spot_reference"`、`symbol == "BTC/USDT"`、`timeframe == "1h"`、`timezone == "UTC"`、`price_unit == "USDT"`、`volume_unit == "synthetic_BTC"`。プロフィールが異なれば非対応として拒否し、別商品・実FX・実市場の記録だと推測して説明しない。`research.entry_wait_bars` は**真偽値を除く整数1（`type(value) is int`）**、`same_instant_policy` は正確な文字列 `"exit_before_signal; signal_recorded_but_no_reentry"` であることも照合する。
- 読み取りには `src/coin1_stage1.py` の `load_record(path)` を使用する。ただし同関数が受理することは、日記に必要な**すべての表示用フィールドが健全**であるという保証ではない。実装②は §5.2 の表示契約を追加確認し、損益計算・OHLCV検査・売買判断の本体を複製しない。

- `load_record()` が受理する `running`／`failed` は、完了済み実験と同程度の事実確認を済ませた意味ではない。§5.3 の部分記録として扱い、最終損益・最終件数・取引確定を表示しない。
- 過去データの実際の到着遅延は計測していない。日記は記録にあるモデル上の時刻・仮定を説明するだけで、実際の情報利用可能性を新たに保証しない。

## 5. 日本語日記の出力契約

### 5.1 共通の表示

`run_id`、記録形式と研究方式の版、`run_status`、実験に使ったデータ源（**人工データ**）・市場・時間足を表示する。`execution.started_at` はプログラム実行日時、`events[].at` と `result.as_of` は**市場時刻**として明示的に区別する。

- 表示時刻は **JST（固定UTC+09:00）** を基本とし、追跡のためUTCの元値も併記する。ホストPCの地域設定に依存させず、元JSON中のUTC文字列は改変しない。
- **同じJSONバイト列から生成する日記本文は毎回同じ**とする。イベントは原本順に表示し、現在時刻・乱数・ファイル更新時刻を本文に追加しない（同じ原本の読取成功を前提とする）。
- `execution.started_at`／`ended_at` はプログラム実行日時、`events[].at` は市場での判断・仮想約定時刻、`result.as_of` は研究上の評価基準時刻とする。`as_of = 07:00 UTC` は**07:00開始足の全OHLCVが確定した意味ではない**。
- 記録内の金額は `Decimal` または元の数値文字列だけを扱い、`float` で再計算しない。初版は原本の精度を保持して表示する。短縮値を付ける場合は「約」と明記する。
- JSONにない原因・予測・市場優位性を日記へ加えない。仮想売買を実際の注文と呼ばない。原本の `source_revision.git_status == "unverified"` を確認済みGitコミットと誤って紹介しない。
- 日記は研究記録の**派生表示**であり、原本の証拠や正式な分析判定に置き換わらない。

### 5.2 `completed` の場合

以下を、**事実・当時の判断・事後の仮想結果・未検証事項**に分けて出力する。

1. **概要**：研究名・版・人工データ・対象期間・評価終了の市場時刻、実行が正常完了した旨。ただし研究の成功や戦略採用を意味しない。
2. **判断集計**：`result.decision_count`、`upper_breakout_count`、`signal_skipped_count`、`closed_trade_count`。必ずJSON由来の値を使う。
3. **時系列**：`events` の原本順で、`event_id` と市場時刻を付して記録する。対応する種類は `upper_breakout`（上方向突破）、`entry_scheduled`（翌足の購入予約）、`virtual_entry`（仮想購入）、`virtual_exit`（仮想決済）、`no_trade`（取引見送り／条件未達）。
4. **判断根拠**：突破／条件未達を説明するときは `source_bar_start_at`、`knowledge_cutoff`、`close`、`prior_n_high`、`N` を**必須**とする。値が不正・欠落なら表示を省いて済ませず拒否する。判断時点より後の価格を理由に追加しない。
5. **見送り理由**：`no_trade.reason` のうち `threshold_not_crossed`＝突破条件未達、`same_instant_as_exit`＝決済優先、`position_already_open`＝保有中、`entry_pending`＝購入予約済み、をそれぞれ区別する。**条件未達の判断と、成立したシグナルの購入見送りを混同しない**。
6. **仮想結果**：記録済み購入・決済時刻、仮想価格・手数料、決済理由、`result.net_pnl_usdt` と `final_cash_usdt` を説明する。未記録の成績指標や勝率・因果関係を生成しない。
7. **制約の明記**：人工データ、履歴モデルの仮想約定、費用仮定、実市場の収益性・約定可能性が未検証であることを固定の注意書きとして出す。

**イベントの扱い**：上記の既知種類以外のイベント（または説明に必要な未知の理由）が混入した完了記録は、意味を推測して一部だけ「正常な完全日記」として出さず、非対応の旨を明示して失敗扱いにする。将来の種類は版別対応として追加する。

**完了記録に限る、イベント別の表示必須契約（§3の追加検証）**：

| イベント | 必須フィールド（全イベント共通の `event_id`・`run_id`・`event_type`・`at` に加えて） |
|---|---|
| `upper_breakout` | `source_bar_start_at`、`knowledge_cutoff`、`N`、`close`、`prior_n_high` |
| `entry_scheduled` | `source_bar_start_at`、`knowledge_cutoff`、`N`、`close`、`prior_n_high`、`intended_open_at` |
| `no_trade` | `reason`、`source_bar_start_at`、`knowledge_cutoff`、`N`、`close`、`prior_n_high` |
| `virtual_entry` | `reference_open`、`buy_price`、`quantity_btc`、`buy_fee_usdt`、`exit_scheduled_at` |
| `virtual_exit` | `entered_at`、`exited_at`、`sell_price`、`sell_fee_usdt`、`net_pnl_usdt`、`close_reason`、`fill_model` |

- 全イベントの識別子・種類・時刻は空でない文字列とし、`run_id` の一致と `event_id` の一意性は既存検証も利用する。**日記に表示する `run_id` と `event_id` は `re.fullmatch(r"[A-Za-z0-9_-]{1,80}", value)` に合致するASCII識別子に限り、省略せずそのまま表示**する（`run_id` は全状態、`event_id` は表示対象の完了イベントに適用）。不正な識別子は拒否し、切り詰めや置換で別のIDへ見せかけない。
- 判断根拠・予約／決済の時刻は明示的なUTCとして解釈し、**日時の値として比較**する。`upper_breakout`・`entry_scheduled`・`no_trade` の `source_bar_start_at + 1時間 == knowledge_cutoff == at` を必須とする（実装①の1時間足・直前確定足ルール専用）。`N` は真偽値を除く整数で研究設定と一致すること。
- 価格・数量・手数料・損益・判断根拠の数値は**有限な十進数文字列**とし、表示に使用する前に型・有限性を確認する。`close` と `prior_n_high` は正の数値とし、上方突破なら `close > prior_n_high`、条件未達なら `close <= prior_n_high` であることを**根拠の整合性として照合**する（市場研究や損益の再計算ではない）。未知の `reason`、`close_reason`、`fill_model` を推測して訳さない。v0.1での決済理由は `fixed_two_hour_holding`、仮想約定モデルは `next_bar_open_plus_adverse_slippage` のみ。
- **最小限の関係性確認（時刻と順序）**：`entry_scheduled` は同時刻の `upper_breakout` に対応し、**`intended_open_at == entry_scheduled.at + 1時間 == 対応する virtual_entry.at`** とする。各 `virtual_entry` には一意な先行予約が対応し、**`exit_scheduled_at == virtual_entry.at + 2時間 == 対応する virtual_exit.at`** とする。`virtual_exit.entered_at`／`exited_at` は対応する購入・決済時刻と一致すること。関連するイベントの原本順序は、予約する突破なら **`upper_breakout` → `entry_scheduled`**、同時刻の決済優先なら **`virtual_exit` → `upper_breakout` → `no_trade(reason="same_instant_as_exit")`** とする。後者の3イベントは同じ時刻であること。重複・孤立・時刻間隔・順序の不整合は拒否する。
- **最小限の関係性確認（同一判断の根拠）**：同じ突破判断から派生した `entry_scheduled`、または `no_trade`（`same_instant_as_exit`／`position_already_open`／`entry_pending`）は、対応する**同時刻の `upper_breakout`** と `source_bar_start_at`、`knowledge_cutoff`、`N`、`close`、`prior_n_high` がすべて一致すること。時刻はUTC日時として、数値は有限な`Decimal`として意味比較する（数値文字列の表記だけに依存しない）。`no_trade(reason="threshold_not_crossed")` は同時刻に対応する `upper_breakout` を持たず、`close <= prior_n_high` を満たすこと。`same_instant_as_exit` は同時刻の仮想決済が存在することも確認する。`position_already_open`／`entry_pending` について、保有／予約の実在を別途検証しない場合は**「記録された見送り理由」**と説明し、状態を独立検証済みと断定しない。**元CSVの再解析・取引ルールの再シミュレーションはしない**。
- 「全イベントを説明する」は**記録に存在する全イベント**を `event_id` 付きで漏らさない意味。正本自体が改ざんされていないことや、存在すべき全イベントが元データから完全に生成されたことを、この表示検証だけで保証しない。既存fixtureの「8イベント」はD03の具体的期待値であり、すべての入力JSONへ一律強制しない。

### 5.3 `failed`／`running` の場合

- `failed`：**「実験失敗・最終評価なし」**と表示する。`errors[]` に理由があれば、各要素が辞書で `stage`・`reason` が安全に扱える文字列であることを確認して説明する。欠損・不正型なら**「理由の記録を確認できない」**とし、`repr()`等で不正な本文をそのまま出さない。最終損益や完了した取引数を推測しない。
- `running`：**「未完了（実行中か中断した可能性がある）」**と表示する。保存済みの `running` だけで現在実際に処理が稼働しているとは判断しない。最終損益や件数を0として表示しない。
- 両状態とも完了イベントの検証を機械的に強制しない。安全に識別・説明できない記録は通常のエラーにする。`failed`／`running` の部分状態報告は**標準出力＋非ゼロ終了**、正常完了だけが**標準出力＋終了0**、不正／非対応の入力は**標準エラー＋非ゼロ終了**とする。

## 6. 異常処理・セキュリティ上の境界

| 状況 | 必須動作 |
|---|---|
| ファイルなし／読取権限なし／空ファイル／JSON破損 | エラーを知らせ、終了コード非ゼロ。正常日記なし |
| 未対応 `record_version` または研究プロフィール | 非対応と明示して拒否。類似した方式と推測しない |
| `completed` と記載されても必要情報・計算・時刻が不整合 | `load_record()` または表示前確認で拒否。成功表示なし |
| `failed`／`running` | それぞれ理由・未完了を明示し、完了損益を表示しない |
| 未知の完了イベント・見送り理由 | 静かに無視せず非対応で拒否 |
| 出力・文字コード等のエラー | 非ゼロ終了。成功を偽装しない |

元JSONを**読取専用**で扱い、内容を書き換えたりファイルを削除したりしない。入力由来の**識別子**（`run_id`・表示対象の `event_id`）は§5.2の安全なASCII文字種・80文字以内を検証し、**省略せずに一意に表示**する。不正な識別子は拒否する。**自由文**（失敗理由など）は、表示前に**改行・C0/C1制御文字（ANSIエスケープを含む）・U+2028/U+2029・双方向表示制御文字（例：U+202A〜U+202E、U+2066〜U+2069）を可視エスケープ表記（例：`\u001b`）に変換し、200文字を超える場合は末尾を省略**する。表示用の文字列変換に限り、元JSONは変更しない。通常の研究日記やエラーにはファイルの**フルパスを表示しない**。例外の生メッセージをそのまま出さず、分類と安全な短文で知らせる。初版ではファイルを外部送信せず、任意のJSON本文をそのまま実行・評価もしない。完了日記は**すべて組み立て・検証してから**標準出力へ出し、途中失敗で完成したように見える文章を残さない。
